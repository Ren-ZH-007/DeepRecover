# APFS 删除记录（未发布）

“电脑恢复”的“解析删除记录”模式新增 APFS：从已释放的文件树节点里找回被删文件的名称、目录、大小、修改时间和数据位置，通过分配检查和覆盖检查的可以预览和导出。原理、实测数据和设计依据见[可行性研究](APFS_FEASIBILITY.md)。

## 支持范围

| 项目 | 说明 |
|---|---|
| 适用来源 | 未加密的外接硬盘、U 盘、外接 SSD 和 APFS 磁盘镜像（原始 `.img/.dd/.raw`，或用 `hdiutil convert -format UDTO` 转出的 `.cdr`） |
| 容器 | 只支持只有一个卷、检查点区连续的容器；块大小 4–64 KiB（只用 4 KiB 测试过） |
| 卷 | 只支持未加密、没有快照、不是系统封存卷的卷；区分大小写和不区分大小写的卷都支持 |
| 找回的信息 | 文件名、完整路径（父目录还在或也能找回时）、大小、修改时间（UTC）、各个数据区段 |
| 碎片文件 | 按区段的逻辑顺序读取，可以导出多区段文件 |
| 没有名称的记录 | 只找到 inode 和区段、找不到目录项时，名称显示为 `APFS_<inode 号>.bin`，仍按同样的检查决定能否导出 |

**不支持（会拒绝扫描并说明原因）**：加密卷（FileVault、加密的外接盘）、有快照的卷（包括 Time Machine 备份盘）、多卷容器（包括 Mac 内置磁盘）、Fusion Drive、系统封存卷、不连续的检查点区。Apple 芯片和 T2 芯片 Mac 的内置磁盘有硬件加密，读出的原始数据无法解析，这一点不能绕过。遇到这些情况仍可以选择签名候选扫描，但加密来源的签名扫描同样找不到内容。

## 检查

每个被删文件只在以下检查全部通过时才提供导出范围，状态为“布局检查通过”（`metadata_checked`）：

1. **布局**：区段从逻辑偏移 0 起连续覆盖文件大小，没有空洞，不超出容器。
2. **分配**：每个数据块在空间管理器的位图里是空闲的，或者在空闲队列里（刚删除、等待回收）；并且不被当前文件树里的任何文件使用。
3. **覆盖检查一**：这些块没有出现在另一个已删除文件的区段里，除非那个文件的记录比当前文件更早（按节点的事务号比较）。
4. **覆盖检查二**：这些块现在不是一个校验和有效的 APFS 元数据对象。

同一个文件在多个旧节点里出现时，每条记录取事务号最新的版本。

通过检查不证明内容完整：如果块被另一个文件用过、而那个文件的记录也已经丢失，就发现不了这次覆盖。和 NTFS 删除记录一样，“布局检查通过”的含义是“支持的布局与分配检查通过”，不是“恢复成功”。PDF、Office、图片、音视频文件可以导出后再用其他工具打开核对。

## 不能导出的情况

| 状态 | 原因 |
|---|---|
| 数据区域已被使用（`allocated_clusters`） | 数据块已被现存文件或其他内容重新占用 |
| 数据可能已被覆盖（`overwritten_after_delete`） | 删除后数据块曾被其他已删除文件或文件系统元数据使用，现在虽然空闲，内容也不可信 |
| 与现存文件共用数据（`shared_with_live`） | 克隆出的副本（如 Finder 复制或 `cp -c`），数据块仍属于一个现存文件；请直接复制现存文件 |
| 暂不支持此布局（`unsupported_layout`） | 透明压缩文件、稀疏文件或带空洞的区段 |
| 元数据检查失败（`invalid_metadata`） | 只找到目录项、没有 inode，或区段有缺口、重叠、不足以覆盖文件大小 |
| 来源范围无效（`invalid_extent`） | 区段超出容器 |
| 分配状态未确认（`allocation_unknown`） | 空间管理器的位图与空闲块计数不一致 |
| 超出大小限制（`size_limit`） | 超过 8 GiB 单文件上限 |
| 达到检查限制（`validation_limit`） | 旧节点里的记录超过扫描上限，覆盖检查一缺少记录，不能确认 |

## 能找到多少

APFS 修改元数据时总是写新节点、释放旧节点，旧节点所在的块很快就会被再次使用。所以删除记录只能找到一部分被删文件，而且无法预测：实测中两个操作完全相同的镜像，一个找回了全部 6 个文件的记录，另一个只找回 2 个。**没找到记录不代表数据已被覆盖**，请再做一次签名候选扫描：连续存放的图片、视频、音频、PDF 和 Office 文档仍可能找回，只是没有原文件名。

## 性能与限制

扫描会顺序读取整个容器一次，用时主要取决于磁盘读取速度。每次最多 10,000 个候选、1,000,000 条元数据记录（当前文件树和旧节点合计）。当前文件树本身超过上限时直接停止；旧节点里的记录超过上限时，已找到的记录仍会入库，但都不能导出（覆盖检查需要全部旧记录），任务标记为未完成。不支持断点续扫。

## 测试

自动化测试使用测试中构造的 APFS 容器（`tests/apfs_fixture.py`，包含检查点、对象映射、空间管理器、空闲队列和文件树），覆盖：名称与路径（现存目录、已删除目录、未知父目录）、多区段文件、节点版本选择、块被现存文件或位图占用、空闲队列中的块、被较新或同一事务的已删除文件覆盖、被元数据覆盖、克隆、压缩和稀疏、区段缺口和越界、只有目录项或只有 inode、空文件、加密 / 快照 / 多卷 / 损坏 / 截断的容器、上限和取消，并对关键检查做了变异测试。另有端到端测试覆盖扫描、入库、读取、校验导出和历史。

开发时另用 macOS 27.2 生成的测试镜像（[`scripts/make_apfs_test_images.sh`](../scripts/make_apfs_test_images.sh)）按清单核对：3 个镜像里通过检查的 19 个文件，17 个和原文件的 SHA-256 一致（其中 6 个只有 inode，按内容核对到原文件），另外 2 个是脚本没有记录内容的填充文件，无法核对；没有发现内容已变却通过检查的文件。旧版 macOS 样本 `wsdf.dmg` 里被删的 PDF 和 Office 文件也全部通过检查，长度与原记录一致，并通过结构校验。这些镜像太大，没有放进仓库。
